# ADR-0007: musl, vendored unchanged, with a VectraOS back end

Status: accepted, 2026-10-01. The import was reviewed by James Kane, 2026-10-01 (`VENDOR.ndb`).

## Context

M4's POSIX personality is musl with a vx back end (01 §9, 04 §6): programs see musl's API unchanged, and the back end turns what musl asks the kernel for into VectraOS: 9Px over the namespace, rings, `posixd`. ADR-0003 asks for pinned, reviewed source with one ADR per import.

## Decision

- **musl 1.2.6**, the latest release, is vendored unchanged under `third_party/musl`. The tarball's signature checks against musl's signing key (fingerprint `8364 8929 0BB6 B70F 99FF DA05 56BC DB59 3020 450F`, from musl.libc.org; confirm it against a second source when reviewing). Licence: MIT.
- **Generated headers**, made once at vendoring as ADR-0003 says, are committed under `ports/musl/generated/`: each architecture's `bits/alltypes.h` and `bits/syscall.h`, and `internal/version.h`, made by the exact commands in musl's `Makefile` (`tools/mkalltypes.sed`, and the `__NR_`-to-`SYS_` `sed`).
- **The build** is `./build`'s, not musl's `make`: the source set and per-file flags of musl's `Makefile` (an architecture's file replaces the generic one of the same name; `-fno-stack-protector` for the start-up and TLS files; `-DCRT` for the crt files), with the flags musl's `configure` chose for the pinned clang, captured once for both architectures. One deviation: frame pointers stay on (`-fno-omit-frame-pointer`, not musl's `-fomit-frame-pointer`), so `dbg` unwinds through libc (05 §4).
- **The back end** never edits musl's tree. musl reaches the kernel through `__syscall0`…`__syscall6` in `arch/<arch>/syscall_arch.h`; `ports/musl/vx/arch/generic/syscall_arch.h`, first on the include path, makes each a call to `__vx_syscall`, the back end's one entry. Eleven of musl's architecture files make system calls in assembly themselves (`clone`, `syscall_cp`, `__unmapself`, `vfork` and the signal `restore` on each architecture, and x86_64's `__set_thread_area`). They are left out of the build (`exclude=` in `ports/musl/port.ndb`), so musl builds the generic C file of the same name instead, whose system calls go through `__syscall` like the rest. Only `syscall_cp`'s generic file is empty: the back end supplies `__syscall_cp_asm` and its `__cp_begin`/`__cp_end` labels.
- **The back end itself** (`ports/musl/vx`, about 1 kLOC) is first-party C23 under the house rules, built into `libc.a` with the mode's flags. It uses vx-rt's system-call stubs, spawn-message reader and stdio, and vx-ns; none of them defines an external symbol, so nothing collides with musl. It keeps the file descriptor table in the process, answers what VectraOS does not do yet with `-ENOSYS` (reported once per number to the kernel log), and has its own `crt1.o`: the kernel enters `_start` with the bootstrap channel, and the back end builds the argument, environment and auxiliary vectors musl's `__libc_start_main` reads from a Linux stack.
- **The sysroot** is `out/<arch>/<mode>/vectra-musl/lib`: `crt1.o`, `crti.o`, `crtn.o`, `libc.a`, compiler-rt's builtins (ADR-0008) and musl's empty `libm.a` and the rest. Programs compile against the vendored headers in place, in the order musl's own build uses, for the target `<arch>-vectra-unknown-musl`, which defines neither `__linux__` nor `__unix__`.
- Only static linking, and no dynamic loader (`ldso/`), until a program needs one.

## Known issues in 1.2.6

- CVE-2026-40200 (`qsort` stack overflow): 32-bit targets only; neither of ours.
- CVE-2026-6042 (pathological slowness in `iconv`'s GB18030 decoder, a denial of service): upstream has a patch. Not carried: the review left the tree as released. Revisit with 1.2.7, or sooner if anything uses `iconv` on untrusted input.

## Consequences

- Upgrading musl is replacing the tree, regenerating the headers, and capturing `configure`'s flags again; the back end's surface is the system-call numbers and the eleven files, which musl rarely changes.
- The back end translates Linux system-call numbers, because that is what musl's sources call. That is the POSIX personality itself, the one exception rule 13 allows, and it stays inside the C library: nothing else in VectraOS sees a Linux number.
