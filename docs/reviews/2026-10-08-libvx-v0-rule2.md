# libvx v0 against rule 2 (2026-10-08)

M6 step 6e4d3, before the level-1 freeze (ADR-0004): every call `libvx` v0 exports, checked against 00 rule 2. *Files are for control and discovery; rings are for bulk. Text is parsed only on the control plane; bulk data and large structures cross by shared pages, never through a parser.* A frozen `libvx.so` carries vx-ns, and so the protocols vx-ns speaks (nsd's among them), so what is wrong here is cheapest to change now.

## The surface, call by call

| Header | What crosses | Verdict |
|---|---|---|
| `<vx/sys.h>` | syscall arguments: binary records | clean |
| `<vx/mem.h>`, `<vx/err.h>` | nothing: arenas, pools and heaps are the process's own memory | clean |
| `<vx/str.h>`, `<vx/fmt.h>`, `<vx/utf.h>` | nothing: pure | clean |
| `<vx/ndb.h>` | text, parsed: the record format of control files (rule 10) | control plane, by design |
| `<vx/time.h>`, `<vx/thread.h>`, `<vx/loop.h>` | binary: clock reads, futexes, port packets, one 64-byte event | clean |
| `<vx/proc.h>`: arguments, `vx_env_get`, `vx_env_set`, `vx_postnote` | text: the spawn message's records, `/env` files, `/proc/N/note` | control plane (small, rare) |
| `<vx/proc.h>`: `vx_proc_spawn`, `vx_proc_exec` | the program's image and its interpreter | **finding 2, fixed** |
| `<vx/file.h>`: reads and writes | 9P over the process's shared-memory rings, binary | clean (rings are for bulk) |
| `<vx/file.h>`: stat, dirread | 9P stat entries, binary; names are text | control plane |
| `<vx/file.h>`: `vx_map` | the server's pages (Tmap) | clean: the bulk path itself |
| `<vx/file.h>`: `vx_ctl` | one ctl message, text | control plane, by design |
| `<vx/file.h>`: `vx_io_submit`, `vx_watch` | the same 9P requests; notify events, binary | clean |
| vx-ns inside `libvx.so`: namespace groups | a group's whole mount table, as text, to nsd and back | **finding 1, open** |

## Finding 1: namespace groups sync their tables as text (decided: option 3, when first needed)

A member of a namespace group (ADR-0009) changes its own table, prints the whole of it as namespace(6) text (`vx_ns_print`, up to 16 KiB) and sends that to nsd in one channel call. nsd keeps it opaque and publishes it in a VMO every member maps. Each member, before resolving its next name, sees the sequence move, empties its table and replays the whole text (`vx_ns_group_apply`).

The page is shared, as the rule asks; what is on it is text that every member parses whole on every change. A namespace is control-plane state (mounts and binds are rare, and the text is what `/proc/N/ns` shows and what a namespace file holds), so this was a deliberate choice in ADR-0009. Its cost is a whole-table print and replay per change per member, lazily, at the member's next walk.

Options:

1. **Keep it** (recommended): the namespace is control plane, 16 KiB is not bulk, and replays are lazy. Record the judgement in ADR-0009, and measure the replay with M7's tracing (7a5's budgets) before changing anything.
2. **Deltas, still text:** nsd keeps a log of change lines beside the whole text; a member applies only the lines past its sequence, and replays the whole text only after a gap. The same format, a fraction of the parsing; nsd's protocol gains a log.
3. **Binary records:** the page holds fixed records (kind, flags, offsets into a string area); members apply them without a parser, and only `/proc/N/ns` renders text. Amends ADR-0009 and nsd's protocol; vx-ns and nsd change (some 300 lines).

**Decided (user, 2026-10-08): option 3, as soon as the first consumer needs it** (a group whose table changes often, or whose replay shows in a trace). Until then the text stays. Recorded in ADR-0009 and the known gaps.

## Finding 2: a spawn copied its image (fixed)

`vx_proc_spawn` and `vx_proc_exec` read the program's image, up to 224 MiB, and its interpreter, through 9P reads into a lazy arena: bulk data crossing by copy. They now map both from their server where it serves Tmap (bootfs, fsd), read-only, and read only from a server that cannot (tmpfs, one dialled over TCP). vxapitest's children, spawned from `/boot/bin`, are mapped, `/lib/ld-vx` with them.

## Outside v0, for later

- rc, svcd and dbg still read whole images into buffers to spawn them (`cmd/rc.c` `load`, `servers/svcd/svcd.c`, `cmd/dbg.c`). They are first-party programs, not `libvx` calls, so the freeze does not hold them; each can map as `vx_proc_spawn` now does.
- `vx_io_submit` makes its requests on I/O threads in level 0 (6e4d2), not as one ring submission: rule 11's batching holds at the API, not yet underneath. The API does not change when it does.
- Large reads go through ring messages, msize at a time. 9Px's dref (`Treadref`) moves a large transfer in one message through a VMO; `vx_pread` could use it past some size, behind the same call.
